:role: Intermediate Detection & Response

:labid: LAB-201-06
:toc:
:icons: font

**Duration:** ~20 minutes

== Overview
Correlate audit logs & monitoring signals.

Correlate API audit events with monitoring signals so you can tell a coherent story about who did what and what the cluster observed.

== Why it matters
Audit logs alone and dashboards alone leave incident stories half-told. Correlating API verbs with monitoring signals lets you prove who did what while the cluster’s health signals confirm impact.

== What does it solve

* Blind spots between “API says X” and “cluster measured Y”
* Slow incident narratives that re-debate timelines
* Missed privilege misuse that never lights a metric alert alone

== Your Mission
Connect audit evidence to monitoring signals so a suspected foothold’s actions and blast radius show up as one coherent story. You already hunted exec on the node in xref:101-09-audit-exec-events.adoc[101-09]; this lab joins that API event to runtime.

=== Prerequisites

* Cluster logging or LokiStack configured (audit indexed)
* Permissions to read audit indices

Click each step only if you need a hint.

.Create project 201-06-a-correlation
[%collapsible]
====
Stay in this project for the sleeper pod.

[source,bash,subs="+macros,+attributes",role=execute]
----
oc new-project 201-06-a-correlation
----

TIP: `Now using project "201-06-a-correlation"`.
====

.Run pod sleeper
[%collapsible]
====
A long-running pod gives you a stable exec target.

[source,bash,subs="+macros,+attributes",role=execute]
----
oc run sleeper --image=registry.access.redhat.com/ubi9/ubi -- sleep 600
----

TIP: `pod/sleeper created`. Wait until it is Running before you exec.
====

.Exec id and uname on sleeper
[%collapsible]
====
This is the suspicious action. Run it so audit records `connect` / `exec`.

[source,bash,subs="+macros,+attributes",role=execute]
----
oc exec sleeper -- sh -c 'id; uname -a'
----

TIP: You should see a uid and kernel string.
====

.Exec on sleeper a second time
[%collapsible]
====
Repeated exec looks like probing, not a one-off debug session.

[source,bash,subs="+macros,+attributes",role=execute]
----
oc exec sleeper -- sh -c 'id; uname -a'
----

TIP: Same output. Two audit events should exist.
====

.Query Loki for exec on sleeper
[%collapsible]
====
If Loki indexes kube-apiserver audit, search `connect` + `exec` + `sleeper`.

[source,promql]
----
{log_type="kube-apiserver"} |= `connect` |= `exec` |= `sleeper` | json
----

TIP: Read `user.username`, `objectRef.name`, verb `connect`, `subresource=exec`, and `sourceIPs[]`.
====

.Grep node audit logs for sleeper exec
[%collapsible]
====
Same hunt as xref:101-09-audit-exec-events.adoc[101-09] if you have control-plane file access.

[source,bash,subs="+macros,+attributes",role=execute]
----
grep sleeper /var/log/kube-apiserver/audit.log | grep exec | tail -1
----

TIP: Parse JSON for timestamp, user, and pod name.
====

.Read sleeper logs from the last two minutes
[%collapsible]
====
Join the audit timestamp to what the container printed.

[source,bash,subs="+macros,+attributes",role=execute]
----
oc logs sleeper -n 201-06-a-correlation --since=2m
----

TIP: The sleep image may log little; empty logs still prove you checked the runtime side. In RHACS, look for a matching process-exec finding.
====

== Detection Logic Draft

Rule: IF (exec to prod namespace pod) AND (user not in admin group) THEN alert severity=high.

Data points:

* Audit: user, verb=connect, subresource=exec
* RBAC: subject group membership
* Namespace label: env=prod
* SIEM enrichment: cluster and namespace labels on forwarded audit events so queries stay simple

== Debrief

Audit shows API intent; logs and metrics show runtime. Correlate on namespace, pod, user, verb, and time to spot pivots that neither stream alone catches.

What breaks without this:

* Siloed audit vs runtime → missed exec campaigns and privilege grants
* No join keys → alerts without investigation context

IMPORTANT: ship audit immutably, align clocks, query by identity and verb, and build anomaly rules (for example non-admin exec in prod).

NOTE: this lab is the foundation for later ACS/IR correlation—not a replacement for runtime sensors.
