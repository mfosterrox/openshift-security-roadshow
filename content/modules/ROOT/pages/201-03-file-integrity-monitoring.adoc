= File Integrity Monitoring & Node Hardening
:labid: LAB-201-03
:cis-summary: "Implement file integrity monitoring and node-level security hardening using the File Integrity Operator."
:mitre-summary: "Detects unauthorized file system changes and implements node-level security controls."
:toc:
:icons: font

**Duration:** ~20 minutes

== Overview
Learn how to deploy and configure the File Integrity Operator to monitor file system integrity on OpenShift nodes, detect unauthorized changes, and implement node-level security hardening measures.

Configure file integrity monitoring and related node hardening so unexpected host file changes become visible and actionable.

== Why it matters
File integrity monitoring detects unauthorized changes to critical system files, which could indicate compromise or misconfiguration. Combined with node hardening, this provides defense-in-depth for the control plane and worker nodes, meeting compliance requirements for system integrity monitoring.

== What does it solve

* Undetected file system tampering
* Compliance monitoring requirements
* Node-level security gaps
* Unauthorized configuration changes
* Security baseline drift

== Your Mission
Turn on File Integrity Operator for worker nodes so a silent binary or config change on the host is a report, not a surprise during incident response.

Click each step only if you need a hint.

.Get pods in openshift-file-integrity
[%collapsible]
====
Confirm the operator is already installed on this cluster.

[source,bash,subs="+macros,+attributes",role=execute]
----
oc get pods -n openshift-file-integrity
----

TIP: Operator pods should be `Running`. If the namespace is missing, install File Integrity Operator from OperatorHub first.
====

.Get FileIntegrity objects cluster-wide
[%collapsible]
====
See whether a scan object already exists before you create one.

[source,bash,subs="+macros,+attributes",role=execute]
----
oc get fileintegrity -A
----

TIP: An empty list is fine. You will create `worker-file-integrity` next.
====

.Apply FileIntegrity worker-file-integrity
[%collapsible]
====
Select worker nodes. Leave debug off unless you are troubleshooting the operator itself.

[source,bash,subs="+macros,+attributes",role=execute]
----
oc apply -f - <<'EOF'
apiVersion: fileintegrity.openshift.io/v1alpha1
kind: FileIntegrity
metadata:
  name: worker-file-integrity
  namespace: openshift-file-integrity
spec:
  nodeSelector:
    node-role.kubernetes.io/worker: ""
  config:
    name: my-file-integrity-config
    namespace: openshift-file-integrity
  debug: false
EOF
----

TIP: `fileintegrity.fileintegrity.openshift.io/worker-file-integrity created` (or configured).
====

.Get FileIntegrity in openshift-file-integrity
[%collapsible]
====
Confirm the object is Accepted / Active before you hunt for reports.

[source,bash,subs="+macros,+attributes",role=execute]
----
oc get fileintegrity -n openshift-file-integrity
----

TIP: `worker-file-integrity` is listed. Status may take a minute to settle.
====

.Get FileIntegrityReports
[%collapsible]
====
Reports appear after AIDE has a baseline. Wait if the list is empty.

[source,bash,subs="+macros,+attributes",role=execute]
----
oc get fileintegrityreports -n openshift-file-integrity
----

TIP: One report per scanned node is typical.
====

.Read FileIntegrityReport results
[%collapsible]
====
Look at the `results` stanza for added, changed, or removed files.

[source,bash,subs="+macros,+attributes",role=execute]
----
oc get fileintegrityreports -n openshift-file-integrity -o yaml | grep -A 10 "results"
----

TIP: An empty change list means the baseline is clean. A hit is a host-file change to investigate.
====

== Debrief

File Integrity Operator is a camera for node-critical paths—catch unexpected file and config changes before they become incidents.

What breaks without this:

* Silent binary or config drift on nodes → malware or misconfig with no early signal
* Compliance asks for FIM with no operator story

IMPORTANT: File Integrity Operator, clear monitored paths, alerting into your ops channel, and pairing with node hardening baselines.

NOTE: focus on critical system/bin/config files; overhead is usually light; intervals are configurable.
